# 7. Checking, testing and export

> Part of the [M4 design](README.md). Decisions: KTD2, KTD11, KTD14, KTD16, KTD17, KTD19 in the [plan](../plans/2026-11-02-1245-feat-m4-pure-subset-plan.md).

The kernel guarantees that a theorem follows from the definitions.
It cannot guarantee that the definitions mean what the C# means: that is the faithfulness gap (design §2).
This chapter is about the engine that runs the pipeline, the tests that narrow the gap, and the outputs M4 produces for people and for Lean.

## The engine

`src/Warrant.Engine` (net10.0) runs everything after extraction (KTD3):

1. It loads the bundle (chapter 1), `tests/data/warrant-semantics.ndjson.gz`, checks it declaration by declaration with the kernel's `ExportChecker`, and freezes the result.
2. For a set of VIR units, it calls `Warrant.Semantics` for their declarations and theorem statements, and admits the declarations, in dependency order, into one fork of the frozen bundle (KTD17).
   A unit that cannot be translated or admitted fails, the units that depend on it are skipped, and the rest go on.
3. It emits and checks proofs for the theorems (chapter 6).
4. It returns per-unit outcomes, assumption reports and, on request, NDJSON.

The engine never sees Roslyn: its input is VIR.
That is what lets M5b's server host it unchanged, and what lets the tests run the pipeline from VIR read back from JSON.
It is untrusted (KTD22): it decides nothing the kernel does not check, except what it reports, and the reports are rendered from data the tests assert on.

In the tests, the bundle is loaded once per run, in a class fixture like the kernel tests' `InitMediumFixture`, and each test works in its own fork.

## Differential tests

For every function in the accepted corpus, a differential test runs the compiled C# and the translated definition on the same inputs and requires the same answer (design §10.5, KTD14).

**Running the C#.** The test emits the *same* `CSharpCompilation` that extraction read into an in-memory assembly and loads it into a collectible `AssemblyLoadContext`.
Using one compilation for both sides means the two cannot drift: there is no second build of the corpus that could use different options.

**Running the model.** For each input the test builds the CIC application `f a₁ … aₙ`, turns the .NET result `r` into a literal, and admits the theorem `f a₁ … aₙ = r` with the proof `@Eq.refl _ (f a₁ … aₙ)` into a scratch fork (KTD14).
The kernel accepts it exactly when the two sides are definitionally equal, which is the same check that proves a C# theorem (chapter 6).
So a passing input is evidence of the same kind as a proved theorem, and could be exported for Lean to re-check.
There is no separate evaluator to trust.

**When they disagree**, the message needs the model's value as well as the CLR's (the engine's read-back, shared with chapter 6).
The test reads it back from the kernel: for an `int` it reduces `BitVec.toNat (Int32.toBitVec t)` to a numeral and reinterprets the bits as signed, `long` is the same with `Int64`, and a `bool` reduces to `Bool.true` or `Bool.false`.
An open enum reads back as its integer.
Read-back does not cover records or closed types: their values are reported as `unknown`.
Read-back is for the message only; the verdict comes from the definitional-equality check.

**Inputs.** FsCheck's default integer generator stays near zero, which never reaches the cases this milestone exists for, so the generators are written by hand:

| Type | Generated values |
|---|---|
| `int`, `long` | `MinValue`, `MinValue + 1`, `-1`, `0`, `1`, `MaxValue - 1`, `MaxValue`, then uniform random values |
| `bool` | both |
| Open enum | every named value, plus unnamed values of the underlying type, including its `MinValue` and `MaxValue` |
| `[Closed]` enum or class | every member, and nothing else |
| Record | fields generated by the rules above |

For methods with up to three parameters, every combination of the boundary values is tried before the random ones.
Unnamed open-enum values matter: without them, a translation that treated an open enum as closed would pass every test.

**Null.** The model has no `null` in M4, so `null` arguments are tested on the C# side only, and what the test requires depends on how the method uses the value:

- A record parameter the method reads: the C# method must throw `NullReferenceException` (the exit criterion in design §11).
- A closed-class parameter, which verified code can only compare: `null` does not throw. On the corpus method `o == A ? 1 : o == B ? 2 : 3` the CLR returns `3`, a value the model cannot produce.
- In every case, the unit's assumptions must say the value is assumed non-null, including records and closed-class values reached through record fields.

The second case is the reason the assumption matters: it is exactly the gap between the model and the CLR, and once M5a quantifies over such a parameter, a proof is only as good as that assumption.

**Closed classes.** For each one, on every pair of static instances, `==`, `Equals(object)` and `EqualityComparer<T>.Default.Equals` must each be true exactly for an instance compared with itself, and reading each instance property twice must give the same object (chapter 3, KTD11).

**Theorems.** Every M4 theorem is a closed `bool` expression, so its truth on the CLR can be computed directly.
For each theorem in `accepted/` and `refuted/`, the test compiles the `Prove.That` argument as a `bool` method in the same compilation, runs it, and requires the engine to report the theorem proved exactly when the method returns `true`.
That checks the trusted statement translation (`Spec.Implies` as `∀`, `>` as a flipped `<`, `==` on records as `$eq`) against the CLR, as the differential tests check function bodies.

## CLR-agreement tests

Differential tests check whole methods.
CLR-agreement tests check each row of the operator table on its own, so a wrong row is found even if no corpus method happens to reach the wrong case (design §10.6).
For each row, the test takes boundary and random operands, computes the result in C# (unchecked), builds the row's CIC term applied to literals of the same operands, and checks the two are definitionally equal.

Both kinds of test turn C# values into CIC literals with the same encoder, so a systematic encoder bug, a sign error on negative numbers for instance, would shift both sides of every comparison together and pass.
So literals are also checked on their own: every `int` and `long` boundary literal, including `int.MinValue` (translated as the negation of `2147483648`, chapter 5), and a random sample, is reduced in the kernel to its bit pattern (`BitVec.toNat` of the literal's bit vector) and compared with the unsigned bit pattern C# computes for the same value (KTD19).

The operations M4 rejects (`/`, `%`, shifts) have their expected CLR behaviour checked now, on the CLR side only.
That includes `int.MinValue / -1` and `int.MinValue % -1`, which the C# specification leaves implementation-defined in unchecked code and which .NET on x64 answers by throwing `OverflowException`, and `-8 >>> 1`, whose logical-shift result Lean's `>>>` on `Int32` does not give.
These are active tests, so a change of runtime or architecture fails now; the model half of each waits for the milestone that admits the operation.

## The other tests

| Test | What it requires |
|---|---|
| Corpus outcomes | Every member in `tests/corpus/m4/` ends in the outcome `expected.json` gives it: translated, proved (and by which proof), false, or rejected with the expected diagnostic and construct name. |
| Bundle roots | Every constant the translator and proof emitter can produce is in `lean/bundle-roots.txt` and in the bundle. A new operator added to the table without re-exporting fails here. |
| Determinism | Extracting the corpus twice gives byte-identical VIR, translating it twice gives identical declarations, and the JSON assumption report is byte-identical across runs. |
| Golden VIR | `Payout`'s VIR matches the committed `tests/Warrant.Vir.Tests/golden/payout.json`, and its unit hash is pinned, so the encoding cannot change without a visible diff. |
| Kernel round trip | The NDJSON written for the accepted corpus loads into an empty environment and checks again. |

## `warrant translate`

M4 needs one command a developer can run on a directory of C# files, and the cross-check script needs it too (KTD16):

```text
warrant translate <directory> [--out <file.ndjson>] [--report <file.md>] [--check-overflow] [--bundle <path>]
```

It compiles every `.cs` file under the directory with the `Warrant.Frontend` factory (chapter 3), extracts VIR, hands it to the engine, and prints one line per unit plus any diagnostics in the compiler's `file(line,col): error CODE: message` format.
`--check-overflow` compiles the files as a project with `CheckForOverflowUnderflow` on would be compiled, and `--bundle` names a semantics bundle other than the one copied next to the CLI. A bundle that declares an axiom besides Lean's standard three, or declares one of them differently from Lean, does not load (chapter 1).
Since M6 (#220) it also loads the attribute sidecar that sits beside the bundle, as `warrant verify` does, so it proves contracts as `verify` proves them; a missing sidecar, or one made for another bundle, is declined with exit code 2.
The start and end of `warrant translate tests/corpus/m4/accepted`:

```text
translating 9 file(s) in tests/corpus/m4/accepted
  Claims.Conversions.Narrow(long)                       translated
  Claims.Conversions.NarrowingKeepsLowBits()            proved (rfl)
  Claims.Conversions.Widen(int)                         translated
  …
  Claims.Records.SamePlace(Claims.Point, Claims.Point)  translated
  Claims.Records.DifferentPoints()                      proved (decide)
65 unit(s): 32 translated, 33 proved, 0 false, 0 undecided, 0 failed, 0 skipped; 0 error(s), 0 warning(s)
```

Units are listed in extraction order: each unit comes after the units it depends on, and ties are broken by documentation-comment ID.
On `rejected/` the same command prints the extraction diagnostics, for example:

```text
tests/corpus/m4/rejected/Arithmetic.cs(11,44): error WRT0002: M4 does not support integer bitwise operator.
tests/corpus/m4/rejected/ClosedClasses.cs(9,14): error WRT0009: Corpus.Rejected.NotSealed is [Closed] but does not have the closed shape: not sealed.
tests/corpus/m4/rejected/Enums.cs(17,13): warning WRT0008: Corpus.Rejected.Starting: closed enum without a member valued 0 can give a [Closed] enum a value the model says cannot exist.
```
The CLI itself is only the Roslyn front end and file I/O; everything between VIR and the outputs is the engine.
With `--out` it writes the bundle followed by every admitted translated declaration, in dependency order, as lean4export NDJSON.
That file loads into an empty environment, which is what Lean's `lean-replay` requires.
Writing admitted declarations needs the conversion from kernel declarations back to export declarations that `CrossCheckFixtures.AdmittedForm` did in the kernel tests; M4 moved it into `src/Warrant.Kernel` as `AdmittedDeclarations`, which finds each inductive's recursors by their generated names instead of scanning the environment (KTD17).

The verb is named so that it does not collide with the existing `warrant export <in> <out>`, or with M5a's planned `verify` and `export --unit`.
Its exit code is 0 when every unit translated and every theorem was proved; 1 when anything was rejected, false, undecided, failed or skipped, or the compilation has errors; and 2 for bad arguments or unreadable input.
That is why false theorems live in `tests/corpus/m4/refuted/`, not in `accepted/` (chapter 2): the cross-check step needs a clean run.

## The assumption report

Each translated unit has an assumption report (design §8.4), as a data structure in the engine with Markdown and JSON renderings.
M4 does not write report files into a project's `obj` directory; that is the build task's job in M5a.
`warrant translate --report` writes the Markdown form, and the tests assert on the data.
This excerpt is from `warrant translate tests/corpus/m4/accepted --report report.md`:

```text
Kernel: Warrant 1.0. Bundle: warrant-semantics sha256:eab5c4e44f05.

Claims.Payments.Validate(Claims.Payment)              TRANSLATED   (kernel: Warrant 1.0, bundle: warrant-semantics sha256:eab5c4e44f05)
  Assumed (parameters):
    - p is not null
  Assumed (global):
    - Arithmetic wraps on overflow (overflow checking is off)
    - The semantics bundle models C# 14 int, long and bool
    - The only axioms are Lean's standard ones: propext, Classical.choice, Quot.sound

Claims.Payments.RejectsZero()                         VERIFIED     (by rfl; kernel: Warrant 1.0, bundle: warrant-semantics sha256:eab5c4e44f05)
  Claim: Validate(new Payment(1, 0, PaymentStatus.Pending)) == PaymentResult.InvalidAmount
  Assumed (from Claims.Payments.Validate(Claims.Payment)):
    - p is not null
  Assumed (global):
    - Arithmetic wraps on overflow (overflow checking is off)
    - The semantics bundle models C# 14 int, long and bool
    - The only axioms are Lean's standard ones: propext, Classical.choice, Quot.sound
```

The kernel is named by the major and minor version of the `Warrant.Kernel` assembly, and the bundle by its file name and the first 12 hex digits of its SHA-256, so a report says exactly which model it rests on.
A unit's status is `TRANSLATED`, `VERIFIED` or `FAILED`; a failed theorem also gives the reason, such as `the claim is false (WRT0001)`.
Reports use C# display names, not Lean names (chapter 5).
A theorem's report inherits the assumptions of every unit it calls, because the claim is only as good as the models it reasons about.
The engine's results refer to VIR node IDs and get their spans from the current extraction, so a report rebuilt from cached results never points at a stale line (chapter 4); M5b extended this from false claims to every position an outcome carries (M5b KTD7).

## The cross-check step

`scripts/cross-check.sh` gains one step after the "C# fixtures" step (design §11, M4 row):

1. `warrant translate tests/corpus/m4/accepted --out "$OUT/m4.ndjson"` must exit 0.
2. Lean's `lean-replay` must accept `"$OUT/m4.ndjson"`.
3. The script prints an `M4 corpus` row, and a failure in either step counts as a disagreement.

Run by hand, the first step ends with `wrote the bundle and 77 admitted declaration(s) to …/m4.ndjson`, and `lean-replay` prints `accepted: 2576 constants`: the bundle's 2,483 constants plus the translated definitions and theorems and the types with their constructors and recursors.

Lean's kernel then checks, independently of Warrant's, that every translated definition and every theorem is well typed, and that each theorem's proof term proves its statement.
It does not check that the definitions model C#: no kernel can.
That is what the differential and CLR-agreement tests above are for.
